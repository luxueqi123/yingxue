# 在线更新与安全回退

管理后台的“系统配置 → 系统更新”只负责管理员鉴权、展示状态和发起操作。真正的 Docker、数据库备份与服务切换由宿主机上的 `open-ai-canvas-host-updater` 执行，业务后端不挂载 Docker Socket。

```text
管理员浏览器 → Backend 管理 API → 带 Token 的 Unix Socket → Host Updater → Docker Compose
```

## 更新来源

在系统更新页面选择并保存来源，随后重新检查版本：

| 预设 | GitHub 版本与更新文件 | 容器镜像 |
| --- | --- | --- |
| 官方直连（默认） | GitHub API、Release、Raw | `ghcr.io` |
| 镜像加速 | `https://gh-proxy.com/` 加原始 HTTPS 地址 | `ghcr.nju.edu.cn` |

展开“分别设置 GitHub 与容器镜像来源”可使用混合配置。GitHub 来源覆盖 Release 列表、目标版本 Compose、Host Updater 二进制和 `SHA256SUMS`；容器来源覆盖 backend、web、yingce-agent，迁移服务复用 backend 镜像。

来源配置保存在宿主机更新器的 `state.json`，独立于部署 `.env`，重启和应用回退不会重置选择。保存新来源会清除上次版本检查及来源检测结果。检查、检测、更新和回退互斥，更新任务记录并固定自己的来源快照；请求失败不会自动切换到其他来源。GitHub Token 只用于官方 API 直连，不发送给 GH-Proxy。

## 映雪一键更新

打开系统更新页时自动检查版本。已有可安装的映雪包时，点一次「一键更新」即开始下载、备份、迁移和切换。页面会自动恢复状态连接。

映雪部署在 Host Updater 的服务环境中分别配置 `CANVAS_UPDATER_REPOSITORY=luxueqi123/yingxue` 与 `CANVAS_UPDATER_UPSTREAM_REPOSITORY=ddcat-ai/open-ai-canvas`。首次接入时应让部署文件的镜像与 `CANVAS_IMAGE_TAG` 对应真实运行版本。代理服务器转发到本地 Web 时，在部署环境中设置 `CANVAS_HTTP_BIND=127.0.0.1`。

同步工作流定时读取影策稳定版，先合并映雪 `main` 和最近通过发布检查的映雪提交，再在候选分支合并上游。合并冲突会中止并上传文件清单。候选通过质量检查、PostgreSQL 测试库的备份恢复和迁移演练后，由工作流自动发布安装包。管理员无需手动上传版本。`yingxue-update.json` 记录对应的影策版本、源码提交与三个应用镜像摘要。

配置了上游仓库时，更新器只接受与当前影策稳定版对应、具有有效验收清单的映雪正式包。Compose 按源码提交读取，镜像按发布清单中的摘要拉取。安装包就绪前，页面自动复查构建结果。

### 在线切换

已有 Nginx 入口的映雪部署可通过 Host Updater 的服务环境启用在线切换。将站点的 `proxy_pass` 指向独立 upstream，在 upstream 块中 include 专用文件。专用文件初始只写 `server 127.0.0.1:3000;`，其中端口取当前 Web 的本机端口。设置 `CANVAS_UPDATER_NGINX_UPSTREAM_FILE` 为专用文件绝对路径，`CANVAS_UPDATER_HEALTH_URL` 为**通过该 Nginx 入口**访问的就绪接口 URL。两个候选本机端口默认为 13001、13002，可以用 `CANVAS_UPDATER_BLUE_PORT` 和 `CANVAS_UPDATER_GREEN_PORT` 调整。与正常升级同样，启用前应核对安装镜像版本和真实运行版本。

点击更新后，现网在镜像拉取、数据库备份、新版启动与检查期间继续服务。候选先使用 `migrate-schema verify` 核对同一 PostgreSQL 的迁移身份和校验和。数据库结构、存储挂载或 PostgreSQL/Redis 拓扑变更会中止在线切换，现网继续运行，涉及这些变更的发布需要维护窗口。支持在线切换的包在清单中声明 `rollingProtocol: 1`。

新版复用数据库、Redis 和媒体数据。每个应用版本使用独立的前端发布根目录，旧资源使用硬链接保留，已打开的编辑页可在保存后刷新。新版健康后，更新器验证 Nginx 配置并平滑重载。通过网站入口验明新版本后，等旧连接退出并停止旧后台，再放行新版后台任务消费。

在线切换验证失败会恢复入口路由，保留切换期间的写入。手工回退同样保留数据库。首次从原编排切到在线发布后，手工回退到原编排需要先停新版任务进程，可能短暂断开。启用后，基础 Compose 管理 PostgreSQL 和 Redis，应用容器由更新器管理，常规运维只重启对应的当前版本容器。

“测试连通性”在宿主机异步执行，页面关闭后仍会继续。检测会查询目标 Release、下载并校验 Compose 配置、验证当前 CPU 架构的更新器校验条目，并读取三个镜像的多架构清单，确认包含当前 `linux/amd64` 或 `linux/arm64`。每项单独显示失败详情，HTTP 403/429 提示拒绝或限流，404 提示版本不存在或镜像尚未同步。

检测不下载完整容器层，也不安装更新器，不能替代更新前的完整拉取与 SHA-256 校验。正式更新在全部准备成功后才停服；通过所选镜像源拉取后，实际 `仓库@sha256:...` 写入 `.env`，不会再因仓库名固定为 `ghcr.io` 而拒绝南大源摘要。回退恢复原 `.env` 和本地旧镜像，使用 `--pull never`；旧镜像被清理时会报错。

镜像服务属于第三方公共服务，其可用性以目标服务器实测为准。SHA-256 与 digest 验证内容完整性，不能单独证明第三方源的发布者身份。

## 安全更新顺序

1. 从 GitHub Releases 读取包含预览版在内的最高语义版本，并与 `.env` 中固定的 `CANVAS_IMAGE_TAG` 比较。`sha-*` 这类非正式镜像标签一律视为低于正式 Release，避免把 `vsha-5509b17` 字典序比较成比 `v1.5.0` 更新。
2. 下载目标版本的 `docker-compose.deploy.yml`，执行 `docker compose config --quiet`，检查部署文件、磁盘空间和当前版本。当前标签不是 `vX.Y.Z` 或 `vX.Y.Z.N` 时，健康检查只确认服务就绪，不要求构建号和镜像标签逐字相同。
3. 创建 `backup-YYYYMMDD-HHMMSS.zip.partial`，其中包含 PostgreSQL custom-format dump、后端数据目录 tar 和元数据；写入完成后 `fsync`、原子改名，并复核 ZIP 结构和 SHA-256。
4. 拉取目标 backend/web 镜像并要求存在仓库 `sha256` 摘要。任何失败都在停服前中止。
5. 停止 web/backend，等待 Backend 的 SIGTERM drain 完成；PostgreSQL 和 Redis 保持运行。
6. 用目标 backend 镜像独立执行 `migrate-schema up`。整批迁移在事务和 PostgreSQL advisory lock 内完成，迁移名称与 checksum 必须匹配。
7. 解析目标 backend/web 镜像的仓库 digest，原子更新 `CANVAS_IMAGE_TAG`、`CANVAS_BACKEND_IMAGE`、`CANVAS_WEB_IMAGE` 和 Compose 文件，启动目标版本；运行容器始终使用 `image@sha256:...`，不使用 `latest`。
8. 连续检查 `/api/health/ready` 的数据库、运行时、schema 和 build version，并经过稳定窗口后才标记成功。

更新状态写入 `/var/lib/open-ai-canvas-updater/state.json`。Backend 或浏览器在切换期间断线不会终止宿主机操作，恢复后可继续读取日志。

## 前端静态文件发布空间

`docker/canvas-web-entrypoint.sh` 先比较镜像发布目录与持久化 Web 目录，只暂存内容发生变化的文件；完整清单仍取自目标版本，不裁剪目标应用。所有复制成功后再发布文件，`index.html` 最后切换。发布清单内的公开目录使用 `0755`、文件使用 `0644`，并修复此前相同内容但权限不正确的路径，避免部署进程的 `umask 077` 让 Nginx 无法读取模型和图片。未变化文件只刷新最近使用时间，保留当前和上一版本分包及既定保留期。

暂存空间按变更文件而非整份静态资产计算，但这不减少 Docker 镜像拉取、数据库备份和回滚副本所需空间。复制失败或已有发布锁时中止，不启动 nginx；旧入口保留。专项验证可运行 `python scripts/test-web-publication.py`，Windows 使用 WSL 执行真实 POSIX 脚本，测试 nginx 替身不启动服务。

## 自动回退

停服后的迁移、启动或健康验证失败会触发自动回退：

1. 停止目标 web/backend；
2. 恢复更新前保存的 Compose 文件；
3. 恢复更新前保存的 `.env`，确保 backend/web 镜像仍绑定到原 digest；
4. 再次校验备份 ZIP 和 SHA-256；
5. 使用 `pg_restore --clean --if-exists` 恢复 PostgreSQL；
6. 启动旧服务并重新进行稳定窗口验证。

回退任一步失败时状态变为 `manual_intervention`，不伪造成功。管理后台仅在存在旧版本和已校验备份时开放人工回退按钮。

## 安装与升级约束

GHCR 镜像部署必须把 `CANVAS_IMAGE_TAG` 固定到具体 Release，并把 `CANVAS_BACKEND_IMAGE`、`CANVAS_WEB_IMAGE` 固定到所选 GHCR 或南大源的 digest，不可使用 `latest` 或仅使用可变 tag。首次安装时显式指定 Release：

```bash
curl -fsSL https://raw.githubusercontent.com/ddcat-ai/open-ai-canvas/main/scripts/install-server-image.sh \
  | sudo env CANVAS_IMAGE_TAG=v1.5.7.1 bash
```

已有部署只安装更新器时，先确认 `.env` 已包含两个 `@sha256:...` 镜像引用，再执行：

```bash
cd /opt/open-ai-canvas
curl -fsSL https://raw.githubusercontent.com/ddcat-ai/open-ai-canvas/main/scripts/install-host-updater.sh | sudo bash
```

脚本会下载与当前 Release 匹配的 Linux amd64/arm64 二进制和 `SHA256SUMS`，生成随机 `CANVAS_UPDATER_TOKEN`，创建 systemd 服务、Socket 目录、状态目录和 `backups/`。Token 只保存在服务器 `.env` 与 root-only 更新器环境文件中。

## 镜像发布与质量门禁

`main` 推送、`v*` 标签和手动发布统一由 `.github/workflows/publish-images.yml` 编排。发布先调用可复用的 `quality.yml`；PR 仍直接运行质量检查。Go 测试、前端格式、类型、Lint、单测和 Chrome E2E 任一失败，都不能进入镜像构建和发布阶段。若仓库规则配置了必需检查，切换后应核对实际 check 名称，避免仍等待旧的独立 push 工作流。

构建和发布分为以下阶段：

1. 校验 `VERSION`；版本标签必须与文件一致，且存在对应 `CHANGELOG.md` 标题。构建时间取提交时间，同一 SHA 不因重跑而改变。
2. 后端分别在 `ubuntu-24.04`（AMD64）和 `ubuntu-24.04-arm`（ARM64）原生编译，保留 CGO 与三个服务/迁移二进制。支付插件在每个平台的镜像阶段重新打包并执行 smoke；PR 则独立执行双架构 smoke，不依赖发布。
3. 前端 Bun 构建阶段固定到 `BUILDPLATFORM`，静态资源只生成一次，再放入 AMD64/ARM64 nginx 镜像。Bun 与 `web/package.json`、质量检查保持 `1.3.9` 一致。
4. 先推送 `sha-<完整提交>-amd64/arm64` 后端镜像及 `sha-<完整提交>-multi` 前端镜像，以摘要 artifact 传递结果。两种后端架构和前端全部成功后，才从摘要合并发布 manifest，不用可变标签作为合并源。
5. 同一 SHA 的 main/tag 发布串行运行；后到的一轮仍经过质量门禁，然后复用已有 SHA 镜像，不重复编译。只有明确的镜像不存在可以转入构建，鉴权、限流、网络和异常摘要必须报错。
6. 发布保留完整 SHA 和短 SHA 标签；只有版本 tag 推送写入具体版本标签。`main` 只有在仍是远端最新提交时才更新 `latest`，旧提交的慢任务不能覆盖新版本。正式部署由安装器和更新器解析并落盘 digest，不依赖 `latest`。

Go 检查显式使用 `backend/go.sum` 作为缓存依赖键，并上传 `go-test-timings`（JSONL），可按 `Test` / `Elapsed` 定位慢测试。Docker 的后端模块下载保留在普通镜像层，编译步骤可以直接读取；支付插件只按实际 import 下载依赖，不重复预取完整后端模块图。版本参数下移到编译入口。GHA 构建缓存按镜像和架构隔离，避免并行任务共用同一 scope。`go-build` cache mount 只用于同一个 builder 内的复用，当前没有额外的跨 Runner mount 导出方案；不能把它当作持久编译缓存。冷缓存首轮和缓存上传仍可能较慢，需要比较连续两轮的实际耗时。

这套发布流程依赖仓库可使用 GitHub 原生 ARM64 Runner、GHCR 写权限以及构建/下载 artifact 能力。首次上线应核对实际 Runner 排队情况、双架构 manifest、main/tag 同 SHA 复用和质量失败阻断；本地测试不能代替这些云端验收。工作流变更不迁移业务数据库，也不修改服务器 Compose 或数据卷。需要回退 CI 时只回退工作流和 Dockerfile 改动；已发布镜像不会自动撤回，线上版本回退仍按本文的备份与迁移约束执行。

## 运维检查

```bash
sudo systemctl status open-ai-canvas-updater
sudo journalctl -u open-ai-canvas-updater -n 200 --no-pager
sudo ls -lh /opt/open-ai-canvas/backups
sudo sha256sum /opt/open-ai-canvas/backups/*.zip
```

备份文件包含业务数据，应限制为 root 访问并纳入异机备份策略。数据卷本身不是备份。
